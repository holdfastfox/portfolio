How I prompt AI to do real work

Patterns worth stealing

Six recurring moves that show up across all four techniques. Each one keeps the work grounded and the scope honest.

  • Ground it in reality. Verify against real source material before deciding — don't let it guess.
  • Supply your own taxonomy. State your mental model directly instead of waiting for it to be inferred.
  • Question your own conclusions. Re-open settled decisions with a quick "is this actually true?"
  • Show, don't describe. Point at a real example instead of describing your style in adjectives.
  • Full version first, then narrow it. Nail the complete spec, then extract the scoped slice.
  • Compress with a guardrail. Say what must survive the cut when asking for shorter.

01 — Claude Code handoff prompts

The common thread: research or design rationale first, then an explicit, scoped, paste-ready spec — never asking Claude Code to make the design decisions itself.

Email template kit → GitHub Pages

The most complete example: a full handoff package, not just a prompt

Started with a single prompt to assemble everything needed for a Claude Code build, then refined it live with one follow-up constraint about GitHub Pages.

Can you give me all of this to give to claude code to build an html page or folder for this?
Assume I'm already connected to gh pages in Claude Code.

That second prompt rewrote BUILD.md to auto-derive the Pages URL from git remote instead of prompting for username and repo. The full package: BUILD.md (executable spec), README.md (human fallback), design-tokens.md (colors and type so nothing gets reinvented), plus source templates and assets.

Reconstructed spec · BUILD.md 
Goal: Host this email kit's assets on GitHub Pages and wire the
send-ready templates to reference the hosted URLs.

Constraints (do not violate):
- Do not restyle or redesign the email templates
- Keep all templates as inline-styled HTML tables (email-client requirement)
- Repo must be public
- Only touch image src attributes and "View in Browser" links

placeholder URLs → build browser-view pages + gallery → wire "View in

Search syntax prototype · three-prompt chain

Build → anchor/QA → scope down

The third prompt in the chain told Claude Code exactly what to remove, what to keep, and what to build — grounded in research on how Sourcegraph, GitLab, Linear, and Honeycomb have approached LLM query parsing.

Assume the two prompts have been built. Write a new prompt that updates the prototype with these changes.

Result: a scoped update spec listing removals (prose parser, concept index, stemming, telemetry), preservations (canonicalizer, happy-path templates), and new builds (autocomplete, tokenized filter pills, silent reformulation on zero results). The research was baked in so Claude Code didn't have to re-derive it.

Status page — column merge & scope-down reconstructed

Broad spec → single component

After settling on the design rationale (Sync as quiet text vs. State as the primary badge), two prompts — one for the full change, one narrowed down to a single component.

Okay let's get a prompt for the existing page that makes this change.
Write this as just the info for the popover.

The second prompt is a pattern worth internalizing: scope a broad handoff down to a smaller one after the design rationale is settled. Claude Code never has to re-derive what the component is for.

Color tokens audit → design-system tool reconstructed

Audit findings packaged for implementation

After an OKLCH ramp rebuild and APCA contrast audit in Cowork, one prompt turned the findings into an implementation-ready handoff.

I want to use your audit findings to implement changes to our internal design-system tool via Claude Code. Can you write markdown to prompt this?

Output: one file, nine sections — ramp replacements, dark-mode defaults, a CVD-enforcement script, an explicitly flagged open design call on an APCA gap, and a "what to leave alone" section. Built so Claude Code wouldn't need to re-derive any value.

02 — Progressive & disambiguating technical explanation

A different skill from handoff prompts: steering an explanation in real time, one constraint at a time, until the mental model is exactly right — then packaging the result. The underlying subject here is internal Moderne architecture, so specifics are intentionally omitted; the value is the technique.

Escalating plainness, same content

Four levels of abstraction from a single starting point

  1. Full technical pass — the real internal mechanics, in engineering terms.

  2. Explain it to me like I'm 5.

    Same ideas, a plain-language analogy, zero jargon.

  3. Can you illustrate this for me?

    Turned the analogy into an actual before/after diagram.

  4. Can you put this visual and the plain-language summary you did in a quick google doc.

    Deliverable assembly — packaging what was already right.

Disambiguating a state model through pointed follow-ups

Questions that restructure the answer

Each of these was a single question that restructured the model — not a new instruction, a pointed check on whether the current answer was actually true.

So in this case wouldn't evicted and not built mean the same thing since a user has to rebuild anything evicted anyway?

Collapsed two proposed states into one, with the reasoning made explicit instead of implied.

I think we're talking about two different things. For the CLI, I think one simple state makes sense. But for the platform side, I think a small set of distinct states are the right things?

Supplied the actual taxonomy split — CLI vs. platform — and had it propagated through the diagram, doc, and panel copy simultaneously.

Can you clean up the 'where the UI status is unclear' — it feels redundant with the blueprint?

A trim prompt against prior output. Not a rewrite request — a specific redundancy catch.

03 — Designing CLI docs for humans and agents

Distinct from everything above: not a spec for an agent to execute, but a design exercise in making the CLI itself legible to agents as a first-class consumer — alongside humans. This is prompting for agent-readable product surfaces, not just prompting an agent to build something.

Moderne CLI · help-text optimization reconstructed prompt sequence

Audit → rewrite → bundle for both audiences

Audited the Moderne CLI's -h output and error messages against GitHub's Primer CLI Design Guidelines, verified against real CLI 4.1.6 behavior — not assumed output.

1. "Audit the Moderne CLI's -h help text against GitHub's Primer CLI
   Design Guidelines. Pull the actual current output from cli-reference.md
   and CLI 4.1.6 — don't guess at what it says."

2. "Rewrite the setup flow as an ordered, scannable table: step, command,
   purpose, required vs. conditional."

3. "Do the same for common errors — pull real error strings and pair each
   with the exact fix command, not a description of the fix."

4. "This CLI increasingly gets driven by coding agents, not just humans.
   Propose a 'bundled docs' concept that works for both audiences —
   machine-parseable but still human-readable."

5. "Package this as a prototype page with the -h rewrites, the
   cli-reference.md preamble, and the bundled docs concept as separate
   sections."

Produced a setup table (step / command / purpose / required-or-conditional), a common-errors-and-fixes table using real error strings (PKIX path building failed, 401 Unauthorized), and a "bundled docs" concept — TROUBLESHOOTING.md, SETUP-CHECKLIST.md, CONFIG-TEMPLATE.yaml shipped at ~/.moderne/docs/ — structured so both a human debugging a setup failure and a coding agent parsing for context can use the same files.

04 — Pressure-testing and scope discipline

A different skill from writing specs: interrogating your own prior conclusions and catching scope problems in real time, through short, pointed follow-ups rather than new instructions.

Pressure-testing your own prior conclusions

Questions that make the model re-derive instead of defend

Is the 'army' problem really a problem…

A prior thread had established that many simultaneous spinners were bad UX. Instead of accepting that as settled, questioning it made Claude re-derive the answer (it's about phase, size, and contrast — not raw count) rather than defend the earlier take.

What if I'm syncing — the progress spinners will be impossible?

Pressure-tested the locked-in spec against a real engineering constraint. Produced a clean fallback contract: spin only if you can sync; if you can't, ship static.

COULD the sequencing bars work per row? If there were less bars?

Steelmanning an option that had already been ruled out, rather than moving on. The side-by-side comparison confirmed the original call was right — for reasons that hadn't been stated yet (motion count, no static form, no subitize-collapse).

Catching scope creep before it lands

Two questions that killed a todo

Gap 2 seems like a huge engineering lift?
It seems like Gap 2 is scope-creep for the initial issue as well?

Two follow-ups, back to back, that got a "todo" item downgraded to investigation-only and then removed from the active checklist entirely. Neither was an instruction — both were noticing something felt off and making Claude justify or correct it.

Grounding a design assumption in real data
Would the failure reason for the LST artifact only live with the sync statuses?

Sent Claude to Slack to check against what engineers actually said, rather than accepting an assumed answer — surfaced a real, acknowledged bug that changed the design brief.

Style transfer via reference, not description
Let's simplify the shit out of this. You can look at [a past issue I filed] as an example of how I write issues.

Instead of describing a writing style abstractly, pointing at a real artifact lets Claude extract the pattern — higher fidelity than adjectives like "concise" or "direct."

Compression with an explicit guardrail
Can you make the to-do list even more succinct.
I don't want you to get rid of important to-dos though.

Paired instructions: compress, but verify nothing substantive was lost. Claude had to show its work (confirmed all 10 original items survived, just merged) rather than produce a shorter list on faith.

Scope control mid-conversation
The ask is to just do this. I just want feedback on how to make this look better.

Cut off a design-rationale re-litigation and redirected to tactical execution — controlling what kind of help is being asked for, not just what the output should be.

Prompts are design briefs in conversation form. The thinking happens before you type.
