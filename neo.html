NEO — building a design system

Building an enterprise design system from near-zero — 1 incomplete component to 78, with full engineering integration.

Role
Design systems lead — audit, architecture, adoption
Context
Enterprise developer-tools platform
Focus
Audit → refactor → adoption
Collaboration
Engineering, design, product teams

The problem

The system existed in name only. One real component — an incomplete Button set — sat in a Figma file alongside ~230 token labels that had never been exported. The bulk of the file was a visual snapshot of the live app, not a design library. Design and code had no connection. Teams built on their best guess.

Constraints

  • Keep teams shipping. No big-bang freeze — change had to land while product work continued.
  • Design ↔ code parity. A token or component had to mean the same thing in Figma and in the codebase.
  • Governance without friction. Consistency that helps teams move faster, not a gate that slows them down.

How I worked

01

Audit

Mapped what existed against what had shipped. Found one real component (Button, incomplete), ~230 Figma-only token labels, and no code connection anywhere.

02

Build

Built 78 components with full state and size matrices. Defined 552 tokens across color, type, spacing, and radius — generated to CSS, JS, and TypeScript on every publish.

03

Integrate

Wired the library to code via 61 Code Connect mappings. An automated consistency checker gates PRs, so parity is enforced rather than audited. Shipped as 3 npm packages over ~10 months.

From file to system

The archive's one real component was Button — 11 variants, 2 missing from the matrix. The shipped system has 7 button-family components, each with a complete state and size matrix. The same pattern repeated across 78 components total. Tokens went from ~230 unshipped Figma labels to 552 generated declarations covering color, typography, radius, shadow, spacing, and grid.

Illustrative — recreated for portfolio; not the production library

Key decisions & tradeoffs

  • Token pipeline, not token labels. The old labels lived only in Figma and were applied by hand. The new system generates CSS, JS, and TypeScript on every publish. A color change in Figma propagates to code without anyone doing it manually.
  • Automated parity over periodic audits. A consistency checker runs on every PR and catches drift before it merges. Design ↔ code parity shifted from a task to a gate.
  • Button family as the founding pattern. Rebuilding the one component that existed meant defining what every component would follow: complete matrices, clear naming, a Code Connect mapping for each variant.

Outcomes

1 component → 78

Started with one incomplete Button set. Shipped 78 components with full state and size matrices, 71 Storybook stories, and 61 Code Connect mappings.

552 tokens, generated

From ~230 Figma-only labels to 552 tokens generated to CSS, JS, and TypeScript on every publish — no manual export.

Parity enforced, not checked

An automated consistency checker gates every PR. Design and code stay in sync without a periodic audit or a person in the loop.

What it taught me

A design system isn't documentation — it's governance. Its real job is to make the right thing the easy thing.
