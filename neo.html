NEO — building a design system

Auditing, refactoring, and rolling out a design system so design and code finally told the same story.

Role
Design systems lead — audit, architecture, adoption
Context
Enterprise developer-tools platform
Focus
Audit → refactor → adoption
Collaboration
Engineering, design, product teams

The problem

The design system had drifted from the product it was supposed to describe. Components had multiplied into redundant variants, design and code disagreed on the details, and teams couldn't trust the library as a single source of truth. The cost showed up everywhere: slower work, inconsistent UI, and decisions relitigated over and over.

Constraints

  • Keep teams shipping. No big-bang freeze — change had to land while product work continued.
  • Design ↔ code parity. A token or component had to mean the same thing in Figma and in the codebase.
  • Governance without friction. Consistency that helps teams move faster, not a gate that slows them down.

How I worked

01

Audit

Ran a reality-alignment audit comparing the system to what had actually shipped, surfacing drift and redundancy.

02

Refactor

Collapsed redundant variants, defined tokens, and connected components to code so the two stayed in sync.

03

Adoption

Wrote pattern documentation and drove the system's first rollout into the product.

From sprawl to system

The clearest win was variant discipline: the most overloaded components had ballooned into dozens of near-duplicate options. Reducing them to a small, intentional set made the system easier to learn, easier to maintain, and far more consistent in the product.

Key decisions & tradeoffs

  • Fewer variants, more intent. Cutting redundant options trades some edge-case flexibility for clarity and consistency — the right trade for a system meant to scale.
  • Code-connect the whole library. Tying components to code made parity self-enforcing instead of a manual chore.
  • Docs as governance. Pattern documentation let the system guide teams without a person standing in the way.

Outcomes

Variants, way down

Collapsed the most overloaded components by roughly four-fifths into a small, intentional set.

Design ↔ code parity

Connected the full component library to code so the two stayed in sync.

Shipped into product

Drove the first rollout and shipped dozens of design fixes along the way.

What it taught me

A design system isn't documentation — it's governance. Its real job is to make the right thing the easy thing.
